# [서비스 메시 1편] 서비스 메시란 무엇인가 - 우리 팀이 도입을 검토하게 된 이유

요즘 회사에서 진행 중인 프로젝트에서 **Kuma 기반 서비스 메시**를 구축하고, **NATS**로 비동기 인터페이스까지 연계하는 작업을 하고 있어요. 내용이 꽤 방대해서 한 번에 다루기는 어려울 것 같아, 앞으로 몇 편에 걸쳐 개념부터 실제 설계 이야기까지 차근차근 정리해보려고 합니다.

첫 편인 오늘은 **"서비스 메시가 대체 뭐고, 왜 필요한가"**부터 짚어볼게요. (참고: 사내 고유 정보나 실제 인프라 수치는 다루지 않고, 일반적인 개념과 설계 관점 위주로 작성합니다 🙂)

## 1. MSA가 커지면서 생기는 문제들

마이크로서비스 아키텍처(MSA)로 시스템을 쪼개기 시작하면 처음엔 서비스 몇 개끼리 REST나 gRPC로 통신하는 정도라 큰 문제가 없어요. 그런데 서비스 개수가 늘어나고 팀도 여러 개로 나뉘기 시작하면, 서비스 간 통신 자체가 하나의 큰 관리 대상이 됩니다.

대표적으로 이런 고민들이 생겨요.

- **암호화**: 서비스 간 통신을 mTLS로 암호화하고 싶은데, 서비스마다 인증서를 직접 관리하고 코드에 TLS 설정을 넣는 건 너무 번거롭다
- **장애 격리**: 특정 서비스가 느려지거나 죽었을 때, 재시도(retry)·타임아웃·서킷 브레이커를 서비스마다 각자 구현하다 보니 팀마다 방식이 제각각이다
- **점진적 배포**: 새 버전을 카나리(canary)나 블루/그린으로 배포하고 싶은데, 이걸 애플리케이션 코드 레벨에서 처리하려니 배포 로직이 비즈니스 로직과 뒤섞인다
- **관측성(Observability)**: "이 요청이 어느 서비스를 거쳐서 어디서 느려졌는지" 추적하려면 서비스마다 트레이싱 라이브러리를 일일이 심어야 한다

이런 것들을 서비스 코드 안에 라이브러리 형태로 넣는 방식(예: 공통 SDK)도 있지만, 언어가 여러 개면 SDK를 언어별로 다 만들어야 하고, SDK 버전을 올리려면 모든 서비스를 다시 빌드·배포해야 하죠. 저희 프로젝트도 서비스가 늘어나면서 정확히 이 지점에서 고민이 시작됐어요.

## 2. 서비스 메시: 통신 로직을 애플리케이션에서 분리하기

**서비스 메시(Service Mesh)**는 이런 "서비스 간 통신에 필요한 공통 기능"을 애플리케이션 코드가 아니라, **인프라 레이어**로 빼내는 접근 방식이에요. 핵심 아이디어는 하나입니다.

> 비즈니스 로직은 비즈니스 로직만 하고, 통신에 관련된 건 옆에 있는 프록시가 대신 처리한다.

이걸 구현하는 대표적인 패턴이 **사이드카 프록시(Sidecar Proxy)**예요.

![사이드카 프록시 패턴 - 서비스는 localhost로 통신하고 컨트롤 플레인이 정책을 사이드카에 배포](/images/service-mesh/sidecar-proxy-pattern.png)

각 서비스 인스턴스 옆에 작은 프록시(대표적으로 **Envoy**)를 하나씩 붙여두고, 서비스가 보내는 모든 요청은 실제로는 이 사이드카를 거쳐 나가고 들어와요. 서비스 코드 입장에서는 그냥 `localhost`로 요청하는 것뿐이고, 재시도·서킷 브레이커·트래픽 분산 같은 건 전부 사이드카가 알아서 처리해줍니다.

이 사이드카들을 한꺼번에 관리하는 게 **컨트롤 플레인(Control Plane)**이에요. "어떤 서비스가 어떤 정책을 따라야 하는지"를 컨트롤 플레인에 선언해두면, 그 설정이 자동으로 관련된 모든 사이드카에 전파됩니다.

| 구성 요소 | 역할 |
| --- | --- |
| 데이터 플레인 (사이드카) | 실제 트래픽 처리 - mTLS, 재시도, 로드밸런싱, 메트릭 수집 |
| 컨트롤 플레인 | 정책 배포, 서비스 디스커버리, 인증서 발급/갱신 |

---

## 3. 서비스 메시가 해결해주는 것들

정리하면, 서비스 메시를 도입했을 때 애플리케이션 코드에서 걷어낼 수 있는 것들이 이 정도예요.

- **자동 mTLS**: 인증서 발급·갱신·회전을 컨트롤 플레인이 알아서 처리, 서비스 코드는 TLS를 신경 쓸 필요 없음
- **트래픽 정책**: 재시도, 타임아웃, 서킷 브레이커, 레이트 리밋을 YAML 정책 몇 줄로 선언
- **트래픽 분할**: 카나리 배포, A/B 테스트용 트래픽 비율 조정을 배포 파이프라인이 아니라 메시 정책으로 처리
- **관측성**: 사이드카가 지나가는 모든 요청의 지연시간, 성공/실패율, 트레이스를 자동으로 수집

물론 공짜는 아니에요. 사이드카가 하나 더 붙는 만큼 리소스 사용량과 지연시간이 소폭 늘고, 컨트롤 플레인 자체를 운영해야 하는 부담도 생겨요. 그래서 "서비스가 몇 개 안 되는 초기 단계"라면 서비스 메시보다 라이브러리 방식이 더 나을 수도 있습니다. 저희 팀도 이 트레이드오프를 두고 상당히 고민했고, 서비스 개수와 팀 구조가 일정 규모를 넘어가는 시점에 도입을 결정했어요.

---

## 4. 왜 하필 Kuma였을까?

서비스 메시 진영에는 Istio, Linkerd, Kuma, Consul Connect 등 여러 선택지가 있어요. 저희는 최종적으로 **Kuma**를 기반으로 구축하기로 했는데, 이 결정 배경과 Kuma의 아키텍처는 다음 편에서 자세히 다룰게요. 간단히 예고하자면:

- Envoy 기반이라 데이터 플레인 자체의 검증된 성능과 생태계를 그대로 활용
- Kubernetes 환경뿐 아니라 VM 등 이기종 환경(Universal 모드)도 하나의 메시로 묶을 수 있는 유연성
- 정책을 선언적인 리소스로 관리할 수 있어 운영 자동화와도 잘 맞아떨어짐
